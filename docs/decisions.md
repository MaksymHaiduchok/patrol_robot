# Журнал архітектурних рішень

## Етап 0 — скелет репозиторію (2026-11-08)

- Звичайний репозиторій з окремими папками без workspaces/Turborepo: кожен сервіс незалежний і запускається окремо, що відповідає модульній архітектурі (будь-який модуль можна замінити).
- web згенеровано `create-next-app` (Next.js 16, App Router, TypeScript, Tailwind 4), api — `@nestjs/cli` (NestJS 12, ESM, strict, Vitest), vision — `uv` (Python 3.12, FastAPI).
- vision має плоску структуру з `main.py` у корені, щоб запускатися як `uvicorn main:app`.
- api слухає порт 4000 за замовчуванням і має увімкнений CORS для web.
- robot і fake-robot поки лише з README і `.env.example`: їхній код — етапи 7–8.
- Секрети тільки в `.env` (у `.gitignore`), у репозиторії — `.env.example`.

## Етап 1 — відео в браузері (2026-11-08)

- Джерело відео задається `PHONE_STREAM_URL`: число — індекс локальної камери (`0` — камера Mac), рядок — URL MJPEG-стріму IP Webcam. Для розробки використовується камера Mac; для замірів (етап 10) — телефон на машинці, бо саме він є камерою робота.
- Кадри читаються в окремому потоці (`FrameGrabber`), зберігається лише останній кадр без черги: так стрім не накопичує затримку, якщо споживач повільніший за камеру.
- Кадр кодується в JPEG один раз у потоці захоплення, а `/stream` лише роздає готові байти — кількість глядачів не впливає на навантаження CPU.
- При втраті джерела потік автоматично перепідключається кожні 2 с; стан з'єднання і FPS видно в `/health`.
- У web відео показується звичайним `<img>`: браузер нативно відтворює `multipart/x-mixed-replace`, а `next/image` для стрімів не підходить (правило eslint `no-img-element` вимкнено).

## Панель оператора — каркас інтерфейсу (2026-11-08)

- Одна сторінка за зразком стрімінгових платформ: зліва керування (режим системи, авто/ручне, рух з клавіатури WASD/стрілками, швидкість, стоп/продовжити), по центру відео, під ним панель стану, справа стрічка алертів. Оператор бачить усе, не перемикаючи сторінок.
- Стан vision і FPS камери беруться з `GET /health` (опитування раз на 2 с); для цього у vision увімкнено CORS (`CORS_ORIGINS`).
- Кнопки керування поки змінюють лише локальний стан: відправка команд з'явиться разом з `OperatorGateway`/`RobotGateway` (етапи 4 і 7).
- MJPEG-стрім ніколи не завершується, тому uvicorn запускається з `--timeout-graceful-shutdown 1`, інакше перезапуск (`--reload`) зависав на відкритому з'єднанні браузера.
- Плеєр вважає стрім втраченим, якщо перший кадр не прийшов за 5 с, і пропонує перепідключитись.

## Перевірка розпізнавання облич до інтеграції (2026-11-08)

- Перед вбудовуванням у систему перевірено, чи достатньо якості YuNet + SFace (OpenCV Zoo), замість готових систем (Frigate + Double Take + CompreFace, студентські репо на YOLOv3/v5 + `face_recognition`/dlib). Готові системи — окремі NVR-продукти через Docker/MQTT, що не вписуються в архітектуру «vision лише детектує, api вирішує»; дрібні репо застарілі й без потокової обробки.
- Скрипт `vision/scripts/face_demo.py`: «свій» з однією фотографією впізнається з cosine similarity ≈ 0.75 при порозі 0.363; незнайоме обличчя позначається «чужим». Якості достатньо — використовуємо YuNet + SFace, як заплановано.
- Моделі завантажує `vision/scripts/download_models.py` у `vision/models/` (не комітиться). Фото для тесту лежать у `vision/faces_demo/` (не комітиться — біометричні дані).

## Етап 2 — детекція людей YOLO11n (2026-11-08)

- Дворівнева схема: YOLO11n шукає людину цілком (видно спиною, збоку, здалеку — коли обличчя ще не видно), а розпізнавання облич (етап 5) працюватиме лише всередині знайдених рамок. Для патрульного робота важливо зупинитись, щойно в кадрі людина, а не коли вона подивиться в камеру.
- Детекція працює в окремому потоці (`PersonDetector`) на останньому кадрі з частотою не більше `DETECTION_MAX_FPS` (10/с). Потік захоплення не чекає YOLO: на кожен кадр стріму малюються останні відомі рамки, тому відео лишається плавним (~30 FPS), а рамки оновлюються 10 разів на секунду.
- Пристрій `mps` (GPU Apple Silicon) з автоматичним fallback на `cpu`. Перший запуск прогріває модель (~8 с) до старту потоку, щоб перший реальний кадр не мав аномальної затримки.
- Перший замір (MacBook, `mps`, тестове зображення 810×1080): середній час інференсу ≈ 35 мс, детекція 9.9/с (обмежена лімітом 10/с).
- `GET /metrics`: FPS захоплення, FPS детекції, середній і максимальний час інференсу (по останніх 100 запусках), кількість людей у кадрі, пристрій.
- Ваги `yolo11n.pt` завантажуються скриптом `scripts/download_models.py` з офіційного репозиторію Ultralytics на Hugging Face у `vision/models/`: автозавантаження Ultralytics з GitHub Releases під час розробки віддавало 504.

## Етап 3 — події в базі даних (2026-11-08)

- Схема з `CLAUDE.md` оформлена міграцією `api/supabase/migrations/20261108120000_init.sql`; додано індекси за `events.created_at` і `face_embeddings.person_id` та обмеження на `events.mode`.
- На всіх таблицях увімкнено RLS без політик: публічний ключ Supabase (є у браузері) не може читати біометричні вектори й події напряму — лише через api, що працює із секретним ключем.
- api: `SupabaseModule` (глобальний клієнт із типізованою схемою) і `EventsModule` (`POST /events`, `GET /events` з пагінацією). Валідація тіла запиту — власною функцією без додаткових бібліотек. `.env` читається вбудованим `process.loadEnvFile()` Node.js.
- vision: `PresenceTracker` перетворює результати YOLO на події з антидребезгом (зникнення < 3 с ігнорується; повторне `person_detected` не раніше ніж через cooldown після `person_left`; події завжди парні). `EventSender` відправляє події в окремому потоці, тож мережа не гальмує детекцію.
- Затримки логуються: vision — час HTTP-запиту до api; api — затримка vision→api (за `ts` події) і час запису в БД. Ці логи — основа для заміру «кадр → реакція» на етапі 10.
- Режим системи (`PATROL`) поки фіксований у `EventsService`; перемикання з web з'явиться разом з `OperatorGateway`.

## Етап 4 — події в реальному часі й оцінка оператора (2026-11-08)

- WebSocket на чистому `ws` (`@nestjs/platform-ws`), а не Socket.IO: у браузері достатньо вбудованого `WebSocket`, а Python-робот (етап 7) підключатиметься тим самим протоколом без додаткових клієнтських бібліотек.
- `OperatorGateway` (`/operator`) розсилає `event_created` після запису події в БД і `event_updated` після змін. Web при відкритті бере останні 50 подій через REST, далі живе на WebSocket, перепідключаючись кожні 2 с.
- Додано людину в контурі: для кожної нової `person_detected` оператор бачить модалку з живим відео — «Чи знаємо ми цю людину?». «Ні» → подія позначається `stranger`; «Так» → «Заповнити дані зараз чи пізніше?»: «зараз» створює запис у `persons` і прив'язує його до події (`known`), «пізніше» — `known_pending`. Модалку можна закрити без рішення.
- Поки розпізнавання облич немає, модалка показується на кожну `person_detected`; з етапу 5 вона спрацьовуватиме на `stranger_detected`.
- Оцінка зберігається в нових полях `events.review_status` і `events.reviewed_at` (міграція `20261108130000_event_review.sql`). Це дає розмічені оператором дані — у розділі експериментів їх можна порівняти з автоматичним рішенням системи.
- Сторінка `/events` — журнал подій із пагінацією по 25.

## Етап 5 — розпізнавання облич (2026-11-08)

- Обличчя шукаються лише всередині рамок YOLO (YuNet на вирізаній ділянці, зменшеній до 640 px), для найбільшого обличчя SFace рахує нормований вектор зі 128 чисел; порівняння — скалярний добуток (= cosine similarity) з усіма векторами «своїх» у пам'яті. Перший замір на камері Mac: ≈ 37 мс на людину в кадрі, детекція лишається ≈ 10/с.
- На відео: «свій» — синя рамка з ім'ям і схожістю, «чужий» — червона, людина без видимого обличчя — зелена «людина». Кирилиця малюється через Pillow; кожен підпис рендериться один раз і кешується, тож 30 FPS стріму не просідають.
- Захист від хибних «чужих»: `stranger_detected` лише після 5 циклів поспіль (~0.5 с) з невпізнаним обличчям; якщо в кадрі одна людина, яку впізнали < 3 с тому, невпізнане обличчя трактується як поворот голови. Компроміс на користь меншої кількості хибних тривог; на етапі 10 його варто оцінити.
- Обличчя «свого» додаються двома шляхами: файлами (1–5 фото) або знімком з камери (`/faces/capture`). Знімок з камери вбудований у модалку: «Так → Зараз → ім'я» одразу зберігає обличчя людини, що стоїть перед камерою, без завантаження файлів.
- Модалка «Чи знаємо ми цю людину?» тепер спрацьовує на `stranger_detected` (раніше — на кожну `person_detected`).
- vision не має доступу до БД: вектори він отримує від api (`GET /persons/embeddings`) при старті й після кожної зміни (`POST /faces/reload`). Фото — у приватному бакеті `faces` лише для перерахунку векторів.
- `POST /persons` приймає тільки ім'я, а фото — окремим `POST /persons/:id/photos` (multipart): так одна й та сама логіка використовується і для нової людини, і для дозавантаження фото існуючій.

## Камера телефона по Wi‑Fi (2026-11-08)

- Джерело відео перемкнено з камери Mac на Android-смартфон з IP Webcam (`PHONE_STREAM_URL=http://<IP>:8080/video`) без змін у коді — підтверджує модульність: джерело відео замінюється одним рядком конфігурації.
- Перший замір (смартфон по домашній Wi‑Fi, MacBook, `mps`): захоплення ≈ 30 FPS, детекція ≈ 9.6/с, YOLO ≈ 21 мс у середньому (макс. ≈ 69 мс), розпізнавання обличчя ≈ 48 мс на людину.

- **Відкинуто:** Freenove 4WD Smart Car Kit (FNK0043) з Raspberry Pi Zero 2W і бортовим кодом на Python (`robot/`). Варіант не реалізовувався; папка лишилась як позначка відкинутого рішення.

- **Обрано:** LEGO Technic Audi RS Q e-tron (42160) з Technic Hub (Control+). Порти перевірено скриптом `pnpm probe`: A — задні колеса, B — передні, D — кермо (усі три — Technic L з енкодером).
- **Архітектура:** бортового комп'ютера немає. Хабом керує `robot-bridge` — процес на Маку (Node.js + TypeScript, `node-poweredup` по Bluetooth LE), який для api виглядає як звичайний робот на WebSocket `/robot`. Протокол api ↔ robot не змінився, тож api і web не залежать від заміни платформи — та сама модульність, що й із заміною камери.
- **Наслідки:** немає датчика відстані й поворотної голови, тому локального оминання перешкод і команди `servo` немає, `distance_cm` у телеметрії — `null`, а в `PATROL` машина сама не їде. У телеметрію додано `hub` (`online`/`offline`) і `battery`.
- **Кермо:** під час підключення міст калібрує кермо, як застосунок Control+: доводить мотор до лівого й правого упору, рахує центр і робочий кут (`STEER_LIMIT_PERCENT` від половини ходу), далі ставить кермо в позицію командою «їхати в абсолютну позицію» з утриманням. Фіксований кут з `.env` (60° мотора) дав надто малий поворот коліс. Ходові мотори — за потужністю; напрям кожного налаштовується в `.env`.
- **Команди моторам — напряму в хаб:** у першій перевірці задній мотор не зупинився після `brake`. `node-poweredup` тримає для порту чергу команд і пускає наступну лише після підтвердження хаба; якщо підтвердження губиться, черга застрягає. Тепер міст шле команди з прапорцем «виконати одразу, без підтвердження» (LWP3, `0x81 … 0x10`), минаючи чергу; кожна нова команда просто замінює попередню. Заодно обійдено помилку бібліотеки в нормалізації кута (кути ≥ 180° перетворювались на −180°).
- **Команда `hide`:** новий маневр за часом (назад → поворот → вперед), параметри в `.env`; після нього робот у `ALERT`.
- **Безпека:** watchdog 2 с без `ping` від api → стоп моторів; при втраті BLE-зв'язку з хабом міст повідомляє `hub: "offline"` і шукає хаб знову.

## Ручне керування з веб-інтерфейсу (2026-11-14)

- api отримав `RobotGateway` (`/robot`): тримає одне підключення робота, шле `ping` щосекунди, з `hello`/телеметрії складає `robot_status` і розсилає операторам лише при зміні. Повідомлення робота й оператора перевіряються вручну (як `events.validation.ts`), без нових бібліотек.
- Команди від web ідуть через уже наявний WebSocket `/operator` (`control`), а не окремим HTTP-запитом: менша затримка і той самий канал, яким приходить статус.
- Web шле `move` лише при зміні напрямку чи швидкості й `stop` при відпусканні; між ними міст тримає останню потужність. Захист від «залиплого» руху: `stop` при втраті фокуса вікна, при виході з ручного режиму, при відключенні оператора (api), і watchdog моста, якщо зник сам api.
- `RobotGateway` не залежить від `OperatorGateway`: оператор підписується на зміни статусу (`onStatus`), тож циклічної залежності модулів немає.

## Повернення додому (2026-11-14)

- **Підхід — повтор шляху у зворотному напрямку, а не навігація до координат.** Не потрібні координати, курс, гіроскоп і планування маршруту, і машина не поїде навпростець крізь перешкоди, які об'їжджала дорогою (датчика відстані немає). За кінематикою автомобіля (bicycle model) машина, що їде назад із тим самим кутом керма, повторює ту саму дугу.
- **Запис:** кожні 20 мс міст записує точку «лічильник коліс + реальний кут керма з енкодера» (якщо щось змінилося хоча б на 2° / 3°). Лічильник — середнє ходових моторів A і B, бо задні крутяться на 5–8% повільніше. Записується будь-який рух: ручний, `hide`, недопрацьоване повернення.
- **Повернення:** точки проходяться з кінця. Шлях ділиться на прогони там, де під час запису змінювався напрям руху (вперед ↔ назад); у межах прогону машина їде без зупинок і по ходу виставляє кермо за записаним кутом у цій точці. Ціль прогону — абсолютне значення лічильника, тож перескок у кінці прогону не переходить у наступний. Наприкінці прогону швидкість падає, а якщо похибка більша за `RETURN_TOLERANCE_DEGREES`, машинка підтягується на малій швидкості.
- **Перша версія (відкинута):** запис відрізків «команда керма вліво/прямо/вправо + градуси коліс» і зупинка після кожного відрізка. На машині: (1) перемикання керма на ходу на 0,2–0,3 с не встигало довести кермо до упору, а повернення ставило повний виворот — дуги не збігалися, машина поїхала не туди; (2) 15 відрізків — 15 зупинок, кожна з перескоком 55–110°; (3) цикл повернення слав команду моторам кожні 20 мс (~100 BLE-записів/с), канал забивався, гальмо й показники енкодерів запізнювались, і міст хибно визначав «застряг». Тепер команди моторам шлються лише при зміні потужності чи кута керма (у симуляції — ~140 записів на все повернення).
- **Випередження керма** (`RETURN_STEER_LOOKAHEAD_MS`): мотор керма повертає із запізненням, тож кермо виставляється для точки трохи попереду. Спершу випередження було в градусах коліс (45°), але на вищій швидкості машина за той самий час проїжджає більше; тепер воно задане часом (90 мс ≈ 45° коліс на 40%) і множиться на виміряну за лічильником швидкість коліс. Пробували піднімати швидкість повернення до 60% (зона сповільнення 180°, випередження 150 мс): повернення стало швидшим, але на машині помітно втратилась точність (прослизання, перескок), тож повернулися до 40% і 120°. У симуляції (запізнення BLE 60 мс, заїзд на 82% з перемиканням керма на ходу) промах без випередження ≈ 9% довжини шляху, з 45–60° — близько 2%; на машині значення треба підібрати.
- **Джерела похибки:** прослизання коліс, люфт керма, різна швидкість запису й повернення (повернення повільніше — менше прослизання), гальмівний шлях. Похибка накопичується з довжиною шляху — тема експерименту на етапі 10.

## Автоматична реакція робота — `DecisionService` (2026-11-17)

- **Рішення ухвалює api, а не vision і не міст.** vision знає лише про кадр, міст — лише про мотори; правила «людина → стоп, свій → їхати далі, чужий → стояти» залежать від режиму системи, стану робота й історії візиту, а це все є тільки в api.
- **Команда до запису в БД.** `onVisionEvent` синхронний і викликається в `EventsService.create` до insert у Supabase, тож затримка «подія → команда роботу» не включає мережевий запит до БД (у тесті на fake-роботі — 0–2 мс усередині api). Лог `decision … → … in N ms (vision→api M ms)` дає дві складові затримки для розділу 5.
- **«Тривога від системи».** Система відпускає робота (`resume`) лише тоді, коли сама його зупинила. Будь-яка команда оператора це скасовує: якщо оператор втрутився, система не поїде сама. Тривога, яку система не вмикала (оператор, `hide`, застрягання), сама не знімається.
- **Свій після чужого.** У межах одного візиту (від `person_detected` до `person_left`) після `stranger_detected` подія `known_person` робота не відпускає: у кадрі може бути двоє.
- **Таймер** відлічується від останньої події про людей, зокрема від `person_left`, тож «через 30 с після виходу людини» робот їде далі.
- **Стан після підключення моста.** Міст стартує в `PATROL` (без маршруту він стоїть, тож це безпечно), а api на `hello` повторює останній `set_state` від оператора. Варіант «api завжди шле `PATROL` на `hello`» відкинуто: після перезапуску api машинка в `MANUAL` із записаним шляхом сама поїхала б маршрутом.
- **Банер у web** тепер показує реальний стан робота (`ALERT` з телеметрії), а не обчислюється з потоку подій. Перемикач «Авто/Ручне» теж бере положення зі стану робота.

## Патрулювання записаним маршрутом (2026-11-17)

- **Проблема:** без датчика відстані машинка в `PATROL` нікуди не їхала, тож автоматична зупинка на людину не мала чого зупиняти.
- **Рішення:** маршрут задає оператор — проїжджає його вручну від точки дому, — а в `PATROL` машинка їздить ним туди-назад тим самим повтором шляху, що й «повернення додому» (лічильник коліс + кут керма, абсолютні цілі прогонів). Нового механізму руху не потрібно, а вже виміряна точність повернення (етап «Повернення додому») переноситься на патруль.
- **Чому туди-назад, а не по колу:** замкнений маршрут вимагав би, щоб машинка точно повернулась у стартову точку — накопичена похибка (прослизання, люфт керма) зсувала б коло з кожним проходом. Шлях туди-назад щоразу прив'язаний до тих самих абсолютних значень лічильника, тож похибка не накопичується між проходами.
- **Пауза й продовження:** `alert` перериває ділянку і зберігає її недопройдену частину; `resume` їде далі з того самого місця. Після завершення патруля шлях від дому до поточної точки знову стає звичайним записом, і «Додому» працює.
- **Обмеження:** перешкоди, яких не було під час запису маршруту, машинка не бачить. Об'їзд перешкод камерою (оцінка глибини) — наступний крок.

## Режим «Стаціонар» (2026-11-17)

Режим системи живе в api (`DecisionService`), а не в браузері: його записують у `events.mode`, і всі вкладки отримують його через `system_mode`. У `STATIONARY` api не шле роботу автоматичних команд і пропускає від оператора лише `stop`; перехід у `STATIONARY` одноразово зупиняє робота. Режим не зберігається між перезапусками api (за замовчуванням `PATROL`) — для прототипу цього достатньо.

## Знімок події та опис від Claude (2026-11-17)

- **Знімок з кадру події.** vision при `person_detected` / `stranger_detected` кодує в JPEG саме той сирий кадр, на якому спрацювала детекція, і тримає 20 останніх за `ts` події; api забирає його через `GET /snapshot?ts=…`. Варіант «api бере останній кадр при отриманні події» відкинуто: між кадром і запитом минає час, і людина могла вийти. Варіант «знімок у тілі `POST /events`» відкинуто: подія збільшилась би в сотні разів, а її обробка має бути миттєвою.
- **Порядок:** команда роботу → запис події → відповідь vision → у фоні знімок → Storage (`snapshots`, приватний бакет) → опис від Claude (лише для `stranger_detected`) → `event_updated`. Помилки знімка чи Claude лише логуються й не впливають на подію.
- **Модель:** `claude-haiku-5-5` — найдешевша й найшвидша; для 1–2 речень опису більшої не потрібно. Мислення вимкнене, ліміт 300 токенів (українська займає більше токенів, ніж англійська, 150 обрізали б речення), таймаут 15 с, один повтор. Промпт прямо забороняє встановлювати особу — Claude описує дії, одяг, предмети й ознаки підозрілої поведінки.
- **Приватність:** кадр із людиною надсилається в зовнішній API (Anthropic). Для прототипу це прийнятно (тест лише на людях, які дали згоду); `CLAUDE_ENABLED=false` вимикає виклик повністю.
- Знімки в web віддаються через `GET /events/:id/snapshot` → `302` на підписане посилання на 60 с, тож ключ Supabase не потрапляє в браузер.

## Інструменти для замірів (2026-11-17)

- `EXPERIMENT_LOG=1` у vision пише CSV `vision/logs/faces-*.csv`: рядок на кожну людину в кожному циклі детекції з висотою рамки й найкращою схожістю обличчя. Найкраща схожість пишеться завжди (і для «чужого»), тож FAR/FRR для будь-якого порогу рахуються з одного запису, без повторних проходів. Папка `vision/logs/` у `.gitignore`: у CSV є імена.
- `vision/scripts/measure_metrics.py` — опитує `/metrics` раз на секунду; `vision/scripts/far_frr.py` — FAR/FRR для порогів 0.30 / 0.363 / 0.40 / 0.45 і частка знайдених облич за висотою рамки.
- Міст після повернення додому й кожної ділянки патруля логує `… done: path length X° wheel, runs N, final error Y°, Z ms`; з `WHEEL_DIAMETER_MM` — ще й у сантиметрах.
- Лог «команда отримана → запис у мотор» усередині моста не робили: команди моторам ідуть по BLE без підтвердження, тож усередині моста це < 1 мс і нічого не говорить про реальну затримку. Затримку «подія → команда» міряє лог `decision`, а мережу api ↔ міст — `ping`/`pong`.

## Вільне патрулювання з об'їздом перешкод камерою (2026-11-17)

- **Чому камера:** датчика відстані на платформі немає; лідар і HC-SR04 від Freenove без Raspberry Pi до хаба LEGO не підключити, датчиків LEGO у наявності немає. Камера вже є на машинці, і об'їзд за нею прямо відповідає темі роботи.
- **Модель:** Depth Anything V2 Small (24,8 млн параметрів, `transformers`) — оцінка відносної глибини з одного кадру. На MacBook (MPS) при вході 448×252 — ~31 мс на кадр, обмежено `DEPTH_MAX_FPS=8`, щоб не забирати GPU в YOLO.
- **Нормування на підлогу.** Модель відносної глибини видає значення з довільним масштабом для кожного кадру, тож поріг на сирі значення не працює. Ділимо близькість у зоні на близькість підлоги в нижній частині кадру: камера закріплена на машинці, і цей шматок підлоги завжди на тій самій відстані. Відношення ~1 — перешкода так само близько, як підлога під носом.
- **Смуга й зони.** Дивимось лише горизонтальну смугу посередині кадру (там перешкоди на висоті машинки, а підлога вже далеко), ділимо на ліво / центр / право. Межі смуги й поріг — у `.env` vision, підбираються на місці; на стрімі видно смугу, значення зон і мініатюру карти глибини.
- **Розподіл ролей:** vision лише оцінює, де зайнято (комп'ютерний зір), рішення про рух ухвалює api (`NavigationService`), міст лише виконує. vision, як і раніше, нічого не знає про робота.
- **Маневр:** машина з кермом не розвертається на місці, тож при перешкоді попереду — назад із кермом від вільного боку, потім вперед у вільний бік. Удар без попередження камери (скло, однотонна стіна впритул) ловиться за лічильником коліс: хід подано, а колеса не крутяться.
- **Безпека:** повільна швидкість (`NAV_SPEED=25`), гальмо без свіжих даних глибини, людина в кадрі зупиняє як і раніше. Міст у `ALERT` не приймає команд руху — інакше команда, яку api надіслав за мить до тривоги, зрушила б машинку.
- **Обмеження:** глибина відносна, а не в сантиметрах; погано бачить скло, дзеркала, глянцеву підлогу; затримка Wi-Fi-відео (150–300 мс) плюс інференс змушує їздити повільно; поріг доводиться підбирати для приміщення.
- **Перевірено** на імітаторах (фейкова vision з керованими зонами, фейковий робот з лічильником): об'їзд вбік, маневр назад-поворот, удар, пауза на людину й продовження, пауза від оператора, гальмо без даних глибини.
